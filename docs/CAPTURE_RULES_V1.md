## 1. 决策流水线（顺序固定，改顺序=改语义）

一条通知进来后依次过 8 道门，**任一道返回 false 就结束**：

| # | 闸门 | 判据 | 典型被拦样本 |
|---|---|---|---|
| 0 | 总开关 / 分来源开关 | `captureMaster`、`captureNotify/Sms/Access` | 用户手动关闭 |
| 1 | 长度 & 垃圾词 | `<6` 字；命中 `JUNK`（验证码/物流/活动…） | 「验证码 123456，正在支付 100 元」 |
| 2 | 黑名单 | 用户点过「以后别再抓这类」 | 招行的营销推送 |
| 3 | 营销渠道 | 通知渠道名/id 命中 `MARKETING_CHANNELS` | 银行 App 的「营销活动」渠道 |
| 4 | 必须有金额（或聊天钱卡片） | 含 `元/¥/￥/人民币`，或聊天类的 `[转账]/[红包]` | 「您有一条新消息」 |
| 5 | 聊天钱卡片（**优先于广告门**） | 聊天类 + `TRANSFER_MARKERS` + 不是银行句式 | 「[转账] 领取了你的红包」 |
| 6 | 广告门 | 命中 `AD_MARKERS` 且无 `PAY_EVIDENCE` | 「4元水电券待领取」 |
| 7 | 资金转移 | 命中 `FUND_TRANSFER_MARKERS` → 放行，后面记成 **TRANSFER** | 「信用卡还款成功 1000 元」 |
| 8 | 非动账模板 | 命中 `NON_TXN_MARKERS`（账单/额度/营销/分期/贷款） | 「本期账单 1,234.56 元」 |
| 9 | 列表页 | 一段文本里 ≥3 笔带单位金额 | 滑动账单明细页 |
| 10 | 来源判定 | 短信 → 直接放行；聊天类 → 标题/卡片判定；**内容/电商 → 只认强支付模板**；支付通道 → 需支付动词 | 抖音「9.9元包邮」 |

> 第 5 道为何在广告门之前：「领取了你的红包」里的「领取」是广告词，但它是真红包。

## 3. 置信度（决定「自动入账」还是「待确认」）

解析基础分（`ParseEngine`）：`40` 起；方向非转账 `+20`；账户匹配 `+15`；商户 `+10`；分类命中 `+10`；强支付动词 `+5`。

抓取校正（`CapturePipeline.effectiveConfidence`）：

| 分支 | 处理 | 结果 |
|---|---|---|
| 读屏（ACCESS） | 封顶 79 | 必进待确认 |
| 通知 + 有结构证据（`TXN_EVIDENCE`） | 按原分 | 常见 88–95 → 自动入账 |
| 通知 + 无证据，但命中强支付模板 | 按原分 | 微信「已支付¥10」→ 90 |
| 通知 + 两者皆无 | 封顶 79 | 进待确认 |
| 聊天类且标题**不是**支付发送方 | 再 `−20` | 群消息 → 低分 |
| 短信 | 不封顶 | 最可靠 |

## 4. 交易身份与去重

身份（`TxnIdentity`）：

```
1) 有交易单号/流水号/订单号/参考号 → ref:<号码>
2) 有卡尾号（尾号8888 / *8888 / 账户3979于…） → card:<尾号>|<金额分>|<5分钟桶>
3) 都没有 → app:<包名>|<金额分>|<5分钟桶>
```

去重分**三档窗口**（这是「微信付款、实际扣银行卡」不重复记账的核心）：

| 档 | 窗口 | 条件 | 用途 |
|---|---|---|---|
| 同渠道 | 150s | 交易身份相同 | 同一条通知被重复投递 |
| 跨渠道·短 | 60s | 同金额 + **不同包名**（微信和银行都是 `NOTIFY`，只能靠包名） | 两条几乎同时到达 |
| 跨渠道·长 | **10min** | 同金额 + **能证明是同一种支付渠道**：本条文本里写着「财付通/微信支付/支付宝/云闪付」，且该渠道 App 最近 10 分钟报过同金额 | 银行动账通知延迟 1~5 分钟的常态场景 |

长窗口的**前提**是「能证明同渠道」，所以不会误合「同金额的两笔真实消费」：
- 同渠道连买两杯 28 元（间隔 90s）→ 第二条不触发长窗（`channelPkg == pkg` 时跳过）→ **记两条**（真机验证）
- 线下刷卡 25 元 + 微信付 25 元 → 银行文本无「财付通/支付宝」→ `payChannelOf = null` → 不触发长窗

**已知残留风险**：如果银行通知**先到**、微信通知**晚于 60s** 才到，仍可能记两条。
（微信通常实时、银行才延迟，这个方向少见；真遇到可手动删一条。）

**刻意不做的事**：不把窗口放宽到几分钟——那会误杀「连买两杯同价咖啡」这类真实的两笔。

## 5. 资金转移（记 TRANSFER，不记支出）

命中 `FUND_TRANSFER_MARKERS`（信用卡还款 / 零钱提现到卡 / 转存）时：

- 记 `TxnType.TRANSFER`：**不进收支/预算/图表**，但明细可见
- **信用卡还款**：需要信用卡账户组成「储蓄卡 → 信用卡」；没有信用卡账户则跳过（页面写明原因和开通方式）
- **取现 / 零钱提现 / 理财申购赎回**：不要求信用卡账户，按**单边转移**记（来源账户减少、目标留空），
  否则这些真实流水会被整条丢弃（v1.2.7 的回归，v1.2.8 修）
- ⚠️ 金额一律以**分**存储（`amountCents`），展示时才换算成元：`50000` = 500.00 元、`5000000` = 50,000.00 元

原因：还款是「资产 ↔ 负债」的转移，记支出会**重复计**（刷卡时已经记过消费）。

## 6. 数据安全（改 schema 前必读）

**这是唯一能一次毁掉全部账目的地方，规则可以错，这里不能错。**

1. `AppDatabase` **不再使用** `fallbackToDestructiveMigration()`。
   加字段必须三件套一起做：
   - `@Database(version = N + 1)` + `DB_VERSION = N + 1`
   - 在 `MIGRATIONS` 里加一条 `Migration(N, N+1)`（只加列用 `ALTER TABLE … ADD COLUMN … NOT NULL DEFAULT x`）
   - 打真机验证：升级前后 `txnCount` 与 `balances` 必须完全一致
2. **迁移前快照**：`SnapshotManager.beforeMigration()` 在 Room 打开数据库之前，读 SQLite 文件头的
   `user_version`，低于目标版本就先复制 `db + -wal + -shm`。判错会导致「该备份时没备份」，所以有单测。
3. **自动快照**：升级后首次启动 / 每天一次 / 手动，各生成一份明文 JSON（私有目录，保留 7 份）。
4. 迁移抛异常时**不要 backfill 一个 destructive fallback 来"修复"**：
   数据文件还在，回装旧版 APK 即可继续用；也可用 `restoredb` 压回迁移前快照。
## 7. 规则库（可编辑）

规则不再写死在代码里，而是 `assets/capture_rules.json`（490 条）。加载优先级：

```
filesDir/capture_rules.json    ← 用户自己改的（App 内「导入规则」或直接放文件）
        ↓ 不存在/解析失败
assets/capture_rules.json      ← 随 App 发布
        ↓ 解析失败
RuleStore.DEFAULTS             ← 代码兜底（保证 App 永远能抓）
```

**加载时校验**（任何一条不过就拒绝该文件、回退下一级）：
- 每张表非空
- 表里没有空词条
- 营销词/非动账/垃圾词 各自 ≥10 条（防止文件被截断还"以为生效了"）

用户入口：设置 → 数据导入导出 → 「识别规则（可自己改）」→ 导出 / 导入 / 恢复默认。

**已验证**（真机对照实验）：同一段文本 `好物100元ABCXYZ`，
用户规则里加了 `ABCXYZ` → `shouldRead=false`；恢复内置 → `shouldRead=true`。

### 7.1 「说人话的规则」（v1.4.0，Backlog P1）

490 条规则对普通用户没有意义：他不知道 `nonTxnMarkers` 是什么，更不知道「淘宝老推送」该动哪张表。
所以 App 里加了一层索引（`capture/RuleGuide.kt` + `ui/RuleGuideCard.kt`）：
用户用大白话说症状（「淘宝老推送券后价」「信用卡账单被记成消费」），
索引给出**该动哪张表 + 该加哪几个词**，点一下就经 `RuleStore.addWords()` 写进
`filesDir/capture_rules.json` 并立即生效 —— 和「导入规则」同一条路径，重启也不丢。

设计约束（`RuleGuideTest` 12 个断言逐条守着）：

| 约束 | 为什么 |
|---|---|
| 每条建议的词必须能落进某张**已存在**的表 | 表名写错 = 用户点了没反应，比没这个功能更糟 |
| 加完必须通过 `Rules.validate()` | 「帮忙」不能把规则改到触发回退内置 |
| 每个词 ≥2 个字 | `junk` 里塞「领取」误杀过真实红包（§9 的教训） |
| 建议词必须是**内置规则里还没有的** | 推荐一个已经存在的词，用户会以为没生效 |
| 18 张表的说明与 `RuleStore.TABLE_KEYS` 一一对应 | 以后加表忘了写说明 = 用户又看不懂了 |

「加词改不了」的三类（退款封顶 79、跨渠道 60s 之后的双记、合并支付拆金额）写成**解释型条目**，
不给按钮 —— 它们是设计取舍/已知边界，不是规则缺失（见 §4、§8）。想精细控制的老路仍然保留：
导出 / 导入 / 恢复默认。

## 8. 退款（冲正，不虚增收入）

退款走 `isRefund()`，处理顺序：

1. 回查 **30 天内同金额的支出**（`TxnDao.findExpenseSameAmount`）
2. 命中 → 判定原因写明 `疑似 #<txnId>「<商户>」（¥x）的退款`，待确认行出现**「冲销原账」**按钮
3. 点「冲销原账」→ **删掉原支出** + 本条不记收入（本月支出减少，而不是收入增加）
4. 不点 → 可正常入账为收入（用户自己判断）
5. **退款一律封顶 79 分**，永远不自动入账 —— 冲销还是当收入，必须用户决定
## 9. 规则变更流程（改之前先看这条）

1. **改表**：只往 `CaptureFilters` / `ParseEngine` 的对应 `listOf` 里加/删，**不要**在 `shouldRead` 里散写 if
2. **补用例**：`CaptureRuleMatrixTest` 加一条真实场景（正/反例）；遍历用例会自动覆盖新词
3. **跑测试**：`:app:testDebugUnitTest` 必须全绿（遍历测试会逐条断言每个词真的生效）
4. **改基线数量**：`CaptureAllRulesTest.规则表规模不低于基线` 里的下限如果因为删词变化，要同步改——**这是故意设的闸门**，防止悄悄放松规则
5. **更新本文附录**：`adb … --es diag "rules"` 抓日志 → 重新生成本文附录 A
6. **真机验证**：用 `probe:`（只判不写）+ `simulate:`（走完整流水线）各跑一遍

> ⚠️ 禁止的操作：为了「少几条待确认」而放宽 `shouldRead`；把 `JUNK`（绝对垃圾）当成通用广告词表用（真实红包曾被 `JUNK` 里的「领取」误杀）。
